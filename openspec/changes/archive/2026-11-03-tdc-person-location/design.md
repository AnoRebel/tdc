## Context

Per-person disclosure withholds in SQL: a value the viewer may not see is never read out of the database (`ListRoomMembersWithDisclosure`, `ViewDirectoryProfile`). The directory encodes visibility as ranks — 0 public, 1 members, 2 hidden — compared with a viewer rank — 0 anonymous, 1 signed in, 2 owner — in generated columns.

## Decisions

### Its own table, the directory's encoding

`user_locations` (sparse, cascading from the account) holds `place`, `mode`, `visibility`, `detected_at` and a generated `location_rank`. A table of its own rather than columns on `user_privacy`: the place is data the person wrote, not a preference, and keeping it apart leaves the directory's rule that it never reads `user_privacy` intact. It sits in the accounts backup part.

### One function, called by every query that returns a person

`person_location(person, viewer_rank, ceiling)` returns the place when `GREATEST(location_rank, ceiling) <= viewer_rank`, else `''`. The member list passes ceiling 0; a directory profile, its search results and its location filter pass the profile's `details_rank`, so a location is never more visible than the profile showing it and a hidden place cannot be found by filtering on guesses. Empty and withheld are indistinguishable, and handlers omit an empty location. A Postgres function rather than a Go helper, so the rule holds where the value is read — the same reasoning as `user_named()`.

The viewer's rank comes from one Go function, `viewerRankOf`: a signed-in account here is 1; a call guest, local or from another server, is 0 — 'members' means signed in on this server.

### Detection on our server, from a bundled list

The client sends `{latitude, longitude}` to `POST /api/me/location/detect`; `places.Nearest` scans GeoNames' towns of 15 000+ people (34 180, 336 KB gzipped, embedded) and answers "Town, Country", or nothing beyond 150 km. The position is not stored, logged or echoed; only the town is saved and the mode becomes automatic. The data file is generated by `go generate ./internal/places` (downloads from GeoNames, deterministic gzip) and committed, so the build never touches the network. *ponytail:* a linear scan with an equirectangular distance — a tenth of a millisecond, run at most every few hours per person; a grid only if it is ever asked in bulk.

### Clients: lazy settings section, lazy refresher

`LocationSetting.vue` is loaded lazily in settings (TanStack Form + Valibot for place and visibility; the directory's `VisibilityPicker`). Pressing "Detect it automatically" is the only thing that can prompt. The refresher is `lib/locationrefresh.ts`, dynamically imported by the app shell on open and on window focus: at most every three hours per device, only if `navigator.permissions` says geolocation is already granted, and only if the setting is automatic. Switching to manual saves the last detected place as the text.

### Migration

Existing `directory_profiles.location` values become `user_locations` rows in manual mode with visibility from the profile's `details_rank` (which already folds in the profile's own visibility), then the column is dropped. The directory editor shows the account location with a link to settings; moderation of a profile still replaces the location, now on the account.

## Risks

- A profile export no longer carries the location; importing an older export ignores it.
- 'Public' reaching other servers is a definition with nothing to carry it yet; federation sends no profile fields today.
