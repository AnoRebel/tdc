## Context

See `proposal.md` for motivation. This document records the technical decisions for outgoing/incoming webhooks, applications, bots, and the remainder of interactive messages, and is explicit about what the foundation change already built versus what this one adds.

Three constraints carry over unchanged from the foundation design:

1. **Zero-cost self-hosting.** No required dependency may be paid, source-available, or AGPL as a default. Delivery, retry, and signing must run against Postgres and the server's own process — no message broker required.
2. **Mobile-first, 1 GB server budget.** A webhook delivery queue is a new source of memory growth if built carelessly (an unbounded retry queue, an unbounded delivery-history table). It must be bounded the same way every other in-process structure in this server already is.
3. **Small operator, no DBA.** Delivery history, retry state, and rate-limit counters live in Postgres tables an operator can inspect with `psql`, not in a second service they now have to run and back up.

### What already exists and what this builds on

Read before designing anything new — duplicating these would be the main risk in this change:

- **`server/internal/apitokens/`** is the credential primitive: scoped tokens, intersected with the account's live permissions on every request (`Restrict`), revocable, shown once. An application's own credential in this change is issued through this same package rather than a second implementation — `apitokens.Service.Issue` already accepts an arbitrary scope and an arbitrary owning account; an application is simply an account-shaped thing that holds one. This is why the applications work in this change is registration, approval, and visibility, not a new credential system.
- **`server/internal/actions/`** defines `Action` (name, label, capability, URL, `once`, `expires`) and `Check`, which validates a message's actions at post time. Selection menus and input fields in this change are new `Capability`-adjacent element kinds added to this same package and the same validation path — not a parallel schema.
- **`server/internal/rooms/presses.go`** is exactly-once button presses: a press is written to a `RecordActionPress` row with a unique constraint before the resulting `action.pressed` event is appended, so a repeat press fails the constraint rather than double-recording. This is the existing answer to "how does a decision get made exactly once"; signed *invocation delivery* to an external integration (below) is a different problem — that event already exists inside the server, this change's job is getting a copy of it, signed, to a program that is not holding a live connection to this server at all.
- **`server/internal/httpapi/description.go`** self-documents every route from the routing table and fails a test if a route lacks an entry. New routes this change adds must gain entries or CI catches it — no new machinery needed here.
- **`server/internal/unfurl/dialer.go`** is a maintained, IANA-registry-driven, connect-time SSRF defence (`net.Dialer.Control`, checked after DNS resolution and immediately before `connect(2)`, closing the DNS-rebinding race that a resolve-then-check approach leaves open — the exact bug Rocket.Chat shipped and was exploited for). `AddressAllowed` and `DialContext` are already exported. Webhook delivery's "outbound request safety" requirement is satisfied by reusing this dialer, not writing a second one.
- **`server/internal/cache/ratelimit.go`** is a `Rates` interface with an in-process and a shared (Valkey-backed) implementation, already used for authentication rate limits. Webhook and interactive-message rate limiting use this same interface with new keys, not a new limiter.
- **`server/internal/events/signing.go`** is the Ed25519 signing and verification machinery events already use, including key rotation with retired keys kept for verifying history. Delivery signing for webhooks and invocations reuses this keyring rather than a second signing scheme — see Decision below.
- **`server/internal/audit/audit.go`** is the append-only audit log with namespaced `Action` constants. Application registration/approval/removal and webhook creation/revocation are recorded here, following the existing pattern (see `ActionCredentialAdded`, `ActionSessionRevoked`) rather than a new logging path.

What is genuinely new: the webhook delivery queue itself (retry, backoff, ordering, history), the applications/bots data model (an application is not an account and a bot is not quite a user, so both need their own tables and their own relationship to rooms and permissions), incoming webhook credentials (channel-bound rather than account-scoped, which `apitokens` does not model), selection menus and input fields as element kinds, message-update/private-response delivery, and per-integration rate limiting as a dimension the existing limiter has not been keyed on before.

## Goals / Non-Goals

**Goals:**

- Outbound webhook delivery that a slow or dead receiver cannot use to degrade the rest of the server, and that survives a receiver being down for a day without either losing events or retrying forever.
- Delivery a receiver can cryptographically prove came from this server, reusing the event-signing keyring rather than inventing parallel key management.
- An application as a real, listed, revocable entity distinct from a personal token, built as a thin layer over the credential mechanism that already exists.
- Full closure of the interactive-messages spec: everything not already built (menus, inputs, update-in-place, private response, signed invocation, per-integration limits, multi-step context) lands in this change.
- Every phase runnable and demonstrable, per house convention.

**Non-Goals:**

- A general-purpose external event bus or message broker. Postgres holds the delivery queue; there is no NATS/Kafka dependency.
- Marketplace or discovery of third-party applications across servers. Registration is local to one server, by an operator or a user with the relevant permission, not a federated app store.
- Guaranteed exactly-once delivery to the receiver. HTTP delivery with retries is at-least-once; the payload's `clientToken`-equivalent (a per-delivery identifier) lets a receiver de-duplicate, but the server cannot guarantee it, because it cannot know the receiver processed a 200 it never saw the response to.

## Decisions

### Outbound webhook delivery: a Postgres-backed queue, not a broker

**Decision.** Outgoing deliveries are rows in a `webhook_deliveries` table: one row per attempt, referencing a subscription and an event. A background worker pool claims pending rows with `FOR UPDATE SKIP LOCKED`, delivers over HTTP with a bounded timeout, and writes the outcome back. Retry uses exponential backoff with jitter, capped at a documented number of attempts (the spec requires a documented limit; this is a configuration value, not a magic number left unstated).

**Why not a broker.** The zero-cost constraint already ruled out a required message broker for realtime fanout, and the same argument applies here more strongly: webhook delivery volume for a TDC-sized deployment is low relative to chat traffic, and a `SKIP LOCKED` claim loop is a well-understood pattern that needs nothing beyond the one datastore every deployment already has. NATS or a broker remains a legitimate future upgrade behind an interface, exactly as the realtime fanout interface already allows swapping Postgres `LISTEN`/`NOTIFY` for Valkey — but is not needed to ship this.

**Ordering.** The spec does not require cross-subscription ordering, only that delivery happens "as they occur." Within one subscription, delivery is attempted in event order (rows claimed oldest-first per subscription), but a later event is not held back waiting for an earlier one's retries to exhaust — otherwise one failing event stalls every event behind it indefinitely, which is precisely the "unbounded notification amplifier / slow receiver stalls other things" failure the proposal calls out to avoid. A receiver that cares about ordering reconstructs it from the payload's own sequence field (the room's existing per-room sequence number, already present on every event) rather than relying on delivery order, which the spec's failure modes make clear cannot be promised once retries are in play.

**Isolation from the rest of the server.** Delivery workers run with their own bounded worker pool and their own HTTP client with a short timeout (single-digit seconds) and no keep-alive to an unresponsive host held open indefinitely. A subscription whose receiver is down for a day accumulates retry rows on its own schedule; it does not hold a goroutine, a connection, or a queue slot that anything else in the server needs. This is the direct answer to "a receiver that is down for a day" and "a slow receiver does not stall anything else" as named failure modes in the proposal.

**Disabling a persistently failing subscription.** The spec requires this rather than retrying indefinitely. A subscription crosses a documented consecutive-failure threshold (attempts exhausted on N consecutive events, or M total consecutive failed attempts across events — the exact figures are a task-time decision, recorded in the spec once chosen) and is disabled, with its owner notified through the existing notification pipeline (`platform/notifications`), not a new one. Disabling stops new deliveries from being queued; it does not delete history.

**Rate limiting shares the excessive-amplification concern.** A subscription is rate-limited using the existing `cache.Rates` interface keyed per subscription, and separately the whole server enforces a ceiling on total outbound webhook concurrency, so a burst of events (a channel getting very active) cannot open an unbounded number of simultaneous outbound connections. Exceeding a limit is recorded and visible to the owner, per the spec's "exceeded limits are visible" requirement — not silently dropped.

### Delivery signing: reuse the event keyring, HTTP Message Signatures shape

**Decision.** Every outbound delivery — webhook event payloads and interactive-message invocations alike, since both are "outgoing deliveries" under the spec's `Delivery signing` requirement — is signed with the server's existing Ed25519 keyring (`events.Keyring`, already built for the event log and already designed for external verification: the federation-readiness test proves a foreign event verifies from only published keys and the event's own content). The signature covers the payload body and a timestamp header, following the same shape as RFC 9421 HTTP Message Signatures that the archived foundation design already chose for the (unbuilt) federation protocol — one signing convention across the server rather than two.

**Why this satisfies "receiver can verify origin" and "replay is detectable."** The timestamp is included in what is signed, so a receiver checks the signature and then checks the timestamp is within a documented window (a small number of minutes) before accepting — exactly the scenario the spec's "replay is detectable" scenario describes. The receiver needs the server's public signing key, published the same way federation would publish it (a well-known path per `KeyPair`/`Keyring.Published()`, already implemented), which means this change's only new surface is *exposing* that existing publication endpoint to an unauthenticated caller, not building key management again.

**Per-integration secret vs. server-wide signature — both exist, for different receivers.** An outgoing webhook subscription also carries a per-subscription shared secret set at creation, and delivery includes an HMAC over the payload using that secret as well as the server's Ed25519 signature. This is deliberate redundancy: the Ed25519 signature is what lets a receiver prove the delivery came from *this server specifically* (useful for a receiver that already trusts this server's identity, e.g. a federation-aware bridge); the per-subscription HMAC is the simpler, more common case most webhook receivers actually implement (compare a header against a secret they configured when creating the subscription, with no key-fetching involved). Documenting both and letting a receiver use whichever it can is cheaper than picking one and being asked why it isn't the other.

### Incoming webhooks: a channel-bound secret, not an account token

**Decision.** An incoming webhook is its own row (`incoming_webhooks`: id, room id, label, token hash, created/revoked, creator) — not an `apitokens` row. The reason `apitokens` does not fit: a token there is scoped to *permissions* an account holds and intersected with the account's live grants on every request. An incoming webhook has no notion of "the account's live grants" — it is bound to exactly one room and can do exactly one thing (post a message), for its own lifetime, independent of any person's permission changes. Modelling it as an `apitokens` row would mean either inventing a synthetic account to hold it (extra indirection for no benefit) or weakening the token model's "intersected with the account's permissions" invariant for this one case. A dedicated table keeps both models honest.

**Leakage is the expected case, not the exception — concretely.** The proposal calls this out and the design has to answer it, not just assert it:

- The credential is opaque, unguessable (same entropy budget as a session token), and prefixed for scanner recognition, following the `tdc_` convention `apitokens` already established, so a leaked webhook URL is at least recognisable as a credential if it turns up in a public repository scan.
- **It can only ever post to the one channel it was bound to at creation** — the spec's "webhook cannot post elsewhere" requirement — so a leaked webhook is a bounded blast radius: whoever has it can spam or forge messages into one channel, attributed to the webhook and never to a person, and can do nothing else. It cannot read the channel, cannot act in any other channel, and cannot be escalated into broader access.
- **Revocation is a single row update and takes effect on the very next request**, because the check is a direct hash lookup with no cache layer sitting in front of it that could serve a stale "still valid" answer — unlike session/permission caching, where the design explicitly accepts eviction-based staleness for read-heavy paths, a security-relevant check like this stays uncached.
- Every incoming webhook's creation and revocation is audited with the actor, and every post through it is attributed to the webhook (not silently as if from a person), so an operator noticing unexpected channel activity can trace it to a specific webhook and revoke it without guessing which one.
- The rate limit on an incoming webhook is per-webhook (via `cache.Rates`), so a leaked credential being hammered by whoever found it degrades only that one channel's ingestion rate, not the server, and the owner is told the limit was hit rather than silently losing events — same requirement as outgoing.

### Applications and bots: a thin layer over accounts and tokens

**Decision.** An `applications` table records name, purpose, requested permissions, approval state, and the room/channel restrictions the spec requires (`Scoped access`, "MUST be restrictable to specific channels or projects"). Approval is a separate step from registration — the spec is explicit that registration alone grants nothing — performed by a user holding the relevant permission, who is shown the exact permission set before approving (the spec's "approval is explicit and informed" scenario).

An approved application is issued a credential through `apitokens.Service.Issue`, scoped to exactly its approved permission set, with the application itself (not a person) as the "owning account" concept — this requires `apitokens` to accept an application as an issuing subject alongside a user, which is the one extension that package needs for this change, not a rewrite of it. This is what makes "an application's access is limited to the permissions it was granted, and does not inherit the approver's authority" (the spec's central scoping requirement) true by construction: the credential is intersected against the application's own granted scope, never against the approving administrator's permissions, because the approving administrator's permissions were never in the intersection to begin with.

**A bot is an application with a room-participant identity.** Rather than inventing a second identity system, a bot gets a row that looks enough like a user for the existing permission, rate-limit, and moderation machinery to treat it as a participant — messages it posts carry its identity, moderators can remove its messages or suspend it exactly as for a human account, and it is subject to the same per-account rate limits already enforced for users, plus an application-level limit on top (the spec's "rate limits and isolation" requirement — misbehaving applications throttled without affecting humans). This reuses moderation's existing "remove message / suspend / restrict" actions against a bot-flagged participant rather than building parallel moderation tooling.

**Removal and content disposition.** Removing an application immediately revokes its credential (same immediate-effect guarantee `apitokens.Revoke` already gives) and the operator is asked whether to retain or remove content the application/bot posted — implemented as the same choice already offered for other account-removal-adjacent flows in moderation, applied here rather than invented fresh.

**External-service disclosure.** An application that declares it sends data externally must say so at registration, and the approval screen must show this before anyone approves it, per spec. This is a field on the `applications` row and a required, not optional, render on the approval screen — the spec's "server functions without external applications" requirement is already true by construction, since nothing else in this change requires an application to exist at all.

### Interactive messages: extending `actions`, not replacing it

**Decision.** Selection menus and input fields are new fields on the existing `Action`-adjacent schema in `server/internal/actions/` (a `select` element carrying options, an `input` element carrying a short text value), validated by the same `Check` function at post time, refused before the message reaches a channel — same principle the existing `Check` already enforces for buttons ("a message that reached a channel and then failed when anybody touched it has already been read, already been trusted").

**Responding to an invocation.** Three response modes the spec requires and today's press flow does not provide, because a press today only ever produces an `action.pressed` event and stops there:

- **Update the originating message** — the response replaces the message's interactive elements atomically. This is implemented as a compare-and-swap on the message's action-state (a version or generation counter incremented on every update), so the "stale activation is rejected" scenario is enforced the same way single-use presses already are: a database-level check, not an application-level race the integration has to avoid itself.
- **Private response** — visible only to the invoking user. This does not go through the room's ordinary event log (which every member can read); it is delivered directly to the invoking user's live connection(s) as a targeted frame, the same way a targeted delivery already happens for per-user state like read receipts, rather than as a room event with per-viewer filtering bolted on.
- **New message** — the ordinary posting path, unchanged.

**Signed invocation delivery to the integration.** This is the genuinely new wire path: today, a press becomes an `action.pressed` *event inside the room*, which the posting program only sees if it holds a live connection and is subscribed — fine for a bot that is always connected, awkward for anything else. This change adds direct signed HTTP delivery of the invocation to a URL the integration registered (reusing the exact signing mechanism described above), so an integration that is not maintaining a live connection still receives invocations reliably, with the same retry/backoff/rate-limiting as outgoing webhook delivery, because structurally it is the same delivery problem — this change's webhook delivery queue serves both.

**Programmatic multi-step conversation.** Context between steps is stored server-side, keyed to (integration, conversation, invoking user), readable only by that resolution — the spec's "no other user can read that state through any interface" requirement — and discarded when the integration or the conversation is removed. This is a bounded key-value table scoped to an application, not a general session store; an application cannot read another application's stored context.

## Risks / Trade-offs

- **A Postgres-backed delivery queue is a new write-heavy table under sustained webhook traffic.** → Delivery attempt rows are the natural retention target: bounded retention (a configurable window, e.g. 30 days) with older rows prunable, mirroring how audit-log retention is already handled. The `SKIP LOCKED` claim pattern is well-proven at far higher volumes than a TDC-sized deployment produces.
- **Dual signing (Ed25519 + per-subscription HMAC) is more for an operator's documentation to cover than one scheme.** → Accepted because it serves genuinely different receivers cheaply; both ride the same delivery pipeline, so it costs one extra header, not a second pipeline.
- **A subscription's disabling threshold is a judgement call with no existing precedent in this codebase to copy.** → Recorded as a task-time decision with the reasoning kept in the spec once chosen, following the same pattern the foundation design used for its own open questions (memory budget figures, federation wire format) — constrain the property now, set the number when there is something to measure against.
- **Extending `apitokens` to issue credentials to an application, not just a user, touches an already-shipped, tested package.** → The extension is additive (a new kind of owning subject) rather than a change to the existing intersection logic for user-owned tokens, and the existing tests for user-owned tokens are the regression guard that the addition must not touch their behaviour.
- **Treating incoming-webhook leakage as the expected case means the design cannot rely on "operators will keep it secret" anywhere.** → Every mitigation above (bounded blast radius, immediate uncached revocation, per-webhook rate limiting, audit trail) holds even in the worst case where the credential is public, which is the bar the proposal sets.
